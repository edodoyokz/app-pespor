# Pespor — delivery dan penerimaan baseline

Rencana ini mengikuti keputusan [PRD](PRD.md), pengalaman [UX](UX.md), kontrak target [TECHNICAL](TECHNICAL.md), serta batasan/dependensi [DECISIONS](DECISIONS.md). Indeks dokumentasi: [README](README.md).

**Status:** baseline rencana, bukan laporan aplikasi lulus. Semua skenario penerimaan di bawah **belum dijalankan**. Dokumen ini tidak mengklaim build, pengujian perangkat, akses layanan produksi, atau integrasi vendor telah berhasil. Persetujuan dokumen hanya membekukan scope awal; bukan izin rilis.

**Otoritas:** dokumen ini memverifikasi scope PRD dan kontrak target UX/TECHNICAL; tidak menambah fitur atau membuat rincian target opsional. Aturan konflik mengikuti README. Daftar dependensi kanonis O-01–O-18 ada di DECISIONS; gate di bawah adalah bukti penutupannya, bukan sumber keputusan terbuka kedua.

## Prototipe dibanding kesiapan produksi

| Hasil prototipe yang berguna | Yang belum dibuktikan olehnya |
| --- | --- |
| Layar dapat dibuka dengan data contoh | Konten resmi tersedia, lengkap, berlisensi, dan diterbitkan oleh operator berwenang. |
| Favorit tampak berubah atau tersimpan selama sesi | Persistensi setelah proses mati, cold start offline, pemulihan data rusak, serta isolasi akun. |
| Login Google/peta/push ditampilkan di UI | Verifikasi identitas backend, aset peta lengkap offline, izin Android, delivery push nyata, serta pengamanan draft. |

| Katalog/keranjang/QR atau status lunas/refund terlihat | Harga/stok server, reservasi atomik, QRIS dan VA nyata, webhook tepercaya, refund penuh terkonfirmasi, serta pengambilan online sekali lintas petugas. |
| Build lokal dapat dibuat | Artefak Android ditandatangani, konfigurasi produksi benar, pemulihan backup diuji, kebijakan privasi dan dukungan operasional siap. |

Tabel ini adalah pembeda bukti, **bukan klaim bahwa fungsi prototipe tersebut sudah ada**. Catatan README lama bukan bukti reverse engineering atau runtime. Implementasi hanya boleh ditandai selesai setelah perubahan sumber dan bukti yang relevan tersedia.

## Urutan implementasi dan ketergantungan

Tidak menetapkan tanggal, jumlah pengguna, SLA, atau target kapasitas tanpa keputusan pemilik produk/operasi. Stack target: mobile React Native + TypeScript + Expo development build; backend Go/PostgreSQL/pgx; admin terpisah React + TypeScript + Vite. Versi Go mengikuti manifest repository, bukan angka baru di rencana ini.

## Checklist implementasi bukan gate rilis

Checklist ini menyatakan bagian yang perlu dibuat, bukan hasil uji atau status selesai:

- **Konten/admin:** identitas stabil dan validasi relasi; draft/aset privat; operator terverifikasi backend; pratinjau; revisi atomik; konflik editor; tindakan push eksplisit dan aman diulang.
- **Mobile/offline:** cache terbit lengkap beserta aset; commit pembaruan tanpa campuran revisi; cold start; pemulihan korupsi; pencarian lokal; pilihan pribadi terpisah dari cache konten; status offline/usia data.
- **Personal/akun:** penyimpanan tamu, merge awal konservatif, sync dengan pengakuan server dan revisi konflik, login ulang saat perlu, logout offline, penghapusan akun online dengan autentikasi ulang; antrean/cache pesanan tidak menyeberang identitas. Profil/pilihan/sesi dibersihkan tanpa menghapus seluruh buku transaksi; retensi minimum, minimisasi PII dan dukungan pesanan belum selesai mengikuti O-11/O-18.
- **Jadwal/notifikasi:** waktu festival eksplisit, lintas tengah malam, konflik ditampilkan, slot batal/hilang ditangani, pengingat lokal 15 menit, izin on/off, rekonsiliasi perubahan, push bukan pengingat lokal atau kanal darurat terjamin.
- **Layanan eksternal:** URL tiket resmi aman dan error state; OAuth/push/signing/storage/gateway sandbox dan produksi dikonfigurasi melalui pengelolaan rahasia, bukan data contoh atau rahasia dalam aplikasi/admin bundle. Gateway belum dipilih; kemampuan QRIS, VA, refund, webhook dan rekonsiliasi harus dibuktikan sebelum rilis.
- **Shop/stok:** SKU unik per varian ukuran/warna, harga/jumlah/total integer IDR server, keranjang lokal bukan reservasi, snapshot harga pesanan berbayar tetap, reservasi stok sampai kedaluwarsa pembayaran, penyesuaian stok atomik/tidak negatif; perubahan commerce tidak mengikuti atau terulang oleh publikasi konten.
- **Pembayaran/refund:** idempotensi durable untuk retry ambigu, signature webhook, deduplikasi/urutan event dan rekonsiliasi provider; callback client bukan bukti lunas. Pisahkan status pesanan/pembayaran/refund. Pembayaran terlambat tidak merebut stok terjual; fulfillment diblokir dan dana direkonsiliasi/refund. Persetujuan pembatalan bukan konfirmasi dana kembali; refund gagal/tidak pasti tidak membuka pickup atau diulang buta.
- **Booth/otorisasi:** petugas Google/allowlist terbatas, validasi server online dan pengambilan lengkap sekali atomik terhadap pembatalan/no-show/refund. Pembeli boleh menunjukkan salinan QR offline dengan peringatan; petugas tidak menyerahkan offline. QR/referensi bukan akses publik ke data sensitif. Tanggal/jam/cutoff dan zona waktu, SOP jaringan/penyerahan dan penanganan no-show refund penuh ditetapkan sebelum penjualan.

Kotak implementasi yang seluruhnya selesai **belum cukup** untuk rilis. Gate rilis memerlukan bukti penerimaan, konten dan operasi di bawah; satu layar berhasil tidak menutup skenario kegagalannya.

## Gate operasional dan rilis

Gate berikut belum dibuktikan; referensi O menunjukkan dependensi kanonis di DECISIONS, bukan daftar keputusan baru. Nilai/PIC yang belum tersedia tetap mengikuti pemilik pada daftar tersebut.

| Gate | Keputusan/bukti yang diperlukan sebelum rilis |
| --- | --- |
| Kepemilikan konten (O-01, O-03, O-04, O-06) | Pemilik resmi data/kontak ditunjuk; edisi/tanggal/venue/zona dan minimal satu kanal tiket dikonfirmasi; aset berlisensi/redaksi disetujui. |
| Pratinjau dan publikasi (O-13) | Operator menjalankan draft → preview → terbit pada konten/aset nyata, termasuk publikasi pertama; draft privat, koreksi revisi salah tidak menambah approval bertingkat. |

Hanya dua peran staf yang disepakati, tanpa approval bertingkat atau role arbitrer. |
| Backup dan pemulihan (O-10, O-11, O-13, O-14, O-18) | Retensi/pemilik/target pemulihan ditetapkan; restore membuktikan revisi terbit, aset/personal dan catatan pesanan/reservasi/pembayaran/refund/pickup serta idempotensi konsisten, tidak mengulangi debit/refund atau membuka pengambilan kedua. |

**Tiket dan shop rilis awal:** minimal satu URL HTTPS kanal tiket resmi yang dikonfirmasi harus dapat dibuka online (FR-09/O-06). URL kosong/tidak aman harus ditangani, bukan pengganti kelulusan. API/kerja sama tiket internal Loket.com/Ticketmelon dan kedua vendor sekaligus bukan gate rilis pertama; tautan resmi tetap wajib. Shop (FR-11–FR-15) memiliki gate gateway/metode/refund, inventaris dan booth sendiri yang semuanya wajib sebelum rilis aplikasi maupun pembukaan penjualan. Ketiadaan vendor/API/kebijakan tidak membolehkan mematikan shop, mengklaim mock lulus, atau memindahkan transaksi ke luar scope. Stamp dan iOS tetap di luar scope; QR pickup shop bukan QR tiket/stamp.

## Cara mencatat hasil saat pelaksanaan

Untuk setiap ID, isi status aktual **Lulus/Gagal/Terhalang**, build/perangkat/revisi yang dipakai, hasil aktual dan lokasi bukti; bedakan dependensi belum tersedia dari bug. Jika terhalang, sebutkan dependensi spesifik dan jangan menandai lulus berdasarkan mock. Pemeriksaan tautan/konsistensi dokumen hanya menilai baseline dokumentasi; tidak menggantikan matriks penerimaan aplikasi atau gate operasional.
